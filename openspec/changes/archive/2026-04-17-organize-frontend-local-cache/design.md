## Context

当前代码中的本地缓存分为两类：
- 已封装缓存：`taskCache`、`projectCache`，具备统一 envelope（`updatedAt + data`）与 TTL。
- 分散缓存：`token`、主题、布局宽度、选中项目、AI 规划草稿在多个组件/模块直接访问 `localStorage`。

现有问题不是“完全没有封装”，而是“封装边界不完整”。业务缓存与 UI/会话缓存采用了不同模式，且缺少集中注册与策略声明，导致：
- 缓存键与版本规则分散维护。
- 同一业务域（任务）存在多份缓存视图（单项目 vs 聚合）时容易出现同步遗漏。
- 调试时难以快速判断数据来自 API 还是本地缓存。

## Goals / Non-Goals

**Goals:**
- 建立统一缓存注册机制，集中声明 key、TTL、scope、schemaVersion。
- 统一缓存访问入口，减少组件内直接 `localStorage` 操作。
- 为任务缓存定义清晰的一致性写入协议，确保清单/Today/本周视图可预测同步。
- 提供最小可用的缓存调试信息（命中、过期、迁移）。

**Non-Goals:**
- 不引入 IndexedDB、Service Worker 或离线优先架构。
- 不改变后端 API 契约。
- 不在本次改动中重构全部历史模块；采用渐进迁移。

## Decisions

### Decision 1: 引入 `cacheRegistry` 作为缓存元信息单一来源
- 方案：新增统一注册表，按 domain 声明缓存条目（key、TTL、version、owner、dataType）。
- 理由：当前 key 分散定义，升级或排障时缺少全局视图。注册表能让策略变更可追踪。
- 备选方案：
  - 继续维持各模块自行定义 key：实现快，但会继续累积不一致。
  - 大规模一次性迁移所有缓存：风险高，回归面过大。

### Decision 2: 保留 `taskCache/projectCache`，在其上抽象统一访问层
- 方案：不推翻现有工具，新增薄封装（如 `cacheClient`）承接统一日志、版本与迁移逻辑。
- 理由：已有缓存工具可复用，低风险演进优于重写。
- 备选方案：
  - 直接重写为全新缓存模块：理论上更整洁，但短期引入较高变更风险。

### Decision 3: 任务缓存采用“双写一致性”协议
- 方案：任务写操作后，同时更新项目维度缓存与聚合缓存；项目全量拉取成功后以项目结果覆盖聚合分片。
- 理由：Today/本周依赖聚合缓存，项目页依赖项目缓存；缺一会导致视图不一致。
- 备选方案：
  - 仅依赖 TTL 过期自动修复：一致性窗口不可控，用户感知明显。
  - 只保留一种缓存形态：会影响当前不同视图的读取性能与改造范围。

### Decision 4: 渐进替换直接 `localStorage` 访问
- 方案：先覆盖高价值点（`tick_selectedProjectId`、AI 草稿、主题），后续逐步迁移其余 UI 偏好键。
- 理由：分阶段交付更易验证，不阻塞业务迭代。
- 备选方案：
  - 一次迁移全部直接访问点：对回归测试与联调压力过高。

## Risks / Trade-offs

- [迁移期间存在新旧入口并存] -> 通过 registry 标注 owner 并加 lint 规则限制新增直写。
- [双写逻辑增加维护复杂度] -> 通过单点 helper（`upsert/remove/sync`）统一调用路径。
- [缓存版本升级导致旧数据不可读] -> 增加版本检测与安全回退（忽略旧结构并触发重拉）。
- [调试信息过多影响性能] -> 仅在开发环境输出详细日志，生产环境保留轻量指标。

## Migration Plan

1. 新增 registry 与 cache client（不改业务行为）。
2. 接入任务缓存一致性 helper，验证 Today/本周与清单更新一致。
3. 将主题、选中项目、AI 草稿迁移到统一入口。
4. 增加规则防止新增直接 `localStorage` 读写（允许白名单）。
5. 完成回归后逐步收敛遗留调用点。

回滚策略：
- 保留原 `taskCache/projectCache` 接口，问题出现时可回退调用层到旧入口。
- registry 仅作为元信息与入口封装，移除时不影响底层存储数据结构。

## Open Questions

- token 是否纳入同一缓存治理层，还是继续保留在鉴权模块单独管理？
- 是否需要在 UI 提供“清空本地缓存”入口（按 domain 清理）？
- 是否需要为缓存命中率和过期率接入埋点，以支持后续优化？
